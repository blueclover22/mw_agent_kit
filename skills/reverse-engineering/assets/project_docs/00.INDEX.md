# Documentation Index — Shared Template (template)

> This document is the **index template for a documentation set that can be copied into other projects as-is**.
> Copy the entire set into `docs/`, then fill in this file's `<...>` placeholders for your project.
> For the procedure when analyzing with Claude (AI), see [`CLAUDE.md`](CLAUDE.md) in the same folder.
>
> **Primary target stacks**: Spring Boot · web (React / Next.js) · Tauri (web frontend + Rust core) · Android.
> The same skeleton can be applied to other stacks (FastAPI / Electron, etc.).

---

This is the documentation index for the `<project-name>` project.
The core documents live directly under `docs/` with a fixed sort order via two-digit numeric prefixes (`00.`–`06.`); per-feature and per-scenario documents live in the unnumbered `domains/` and `processes/` folders. This index provides the overall guide to categories and roles.

This set records **the current facts (is) observed in the code** of an existing project. Each document directly contains "this project's conventions/facts", and the same topic is never split across multiple documents (§Per-Topic SSOT).

When adding or removing documents, update this index's tables, category guide, and `related_to` together.

## Category Guide

### Meta (00)

Indexes all documents as inbound links and holds the §Domains / §Processes registries; excluded from bidirectional symmetry (§Frontmatter Conventions).

### Overview (01)

The **fact sheet connecting the conventions of the other documents to the current project**. Holds only project-specific information that has no home elsewhere (Scope · Tech Stack · directory tree · entry points · environment variable keys · Change Checklist · Troubleshooting). **Conventions themselves are linked, not duplicated here.**

### Foundation (02–04)

**Reference documents** with the lowest change frequency, referenced by all other documents. In case of conflict, Foundation takes precedence. `02` = structure and dependency direction, `03` = how code is written (naming · errors · security), `04` = how the framework/runtime is used, including the external interface contract catalog.

### Layer (05)

**Horizontal** conventions per layer — UI layer and core / data layer, in one document per project. Per-stack mapping — see the table under §Table of Contents. `02` says what the layers are and how they depend on each other; `05` says how code inside each layer is written.

### Operations (06)

Procedures and artifact locations at build · verification · test · deploy · run · operations time.

### Domain (`domains/`)

**Vertical** slices — one feature/subsystem per file (entities · state machines · domain rules · contract links). Leaf documents: they reference the core one-way; the core does not back-reference them. Registered in §Domains.

### Process (`processes/`)

Call chains of representative scenarios — one scenario per file (chain at a glance · step-by-step details · sequence). Leaf documents like `domains/`. Registered in §Processes.

## Per-Topic SSOT (Single Source of Truth)

**The same topic is never split across multiple documents.** The original (SSOT) for each topic lives in exactly one place below; other documents keep only a one-line summary + link. This rule is the key to preventing duplication in the documentation set.

| Topic | SSOT | Treatment in other documents |
| :--- | :--- | :--- |
| Naming conventions (files · variables · functions · types) | **03** §2 Naming | 02 · 01 link only |
| Domain term names (same concept = same word) | **03** §2 Domain Terms | `domains/` link only |
| Architecture principles · layer boundaries · dependency direction | **02** | 01 shows only this project's directory tree; 05 assumes 02's layer definitions |
| External interface contracts (API · command · Intent) | **04** §5 Contract Catalog | 05 · `domains/` · `processes/` link only |
| Per-layer coding conventions (UI · core / data) | **05** | `domains/` link only |
| Environment variable key list · value policy | **01** §4 Environment Variables | 06 covers only build-time injection; 04 only the loading mechanism |
| Directory tree · entry points | **01** §3 Current Structure | `processes/` cite entry points by path, never redefine them |
| Build · verification pipeline · test execution · conventions | **06** | 01 · 03 link only |
| Call chains of user scenarios | **`processes/`** (one file per scenario) | 02 · `domains/` link only |
| Feature-domain rules · entities · state machines | **`domains/`** (one file per domain) | 05 links only |

Error handling is split by layer with mutual links (not duplication): **03** = general policy (types · propagation · logging), **04** = framework-level mechanisms, **05** = service · transaction boundaries.

> If, while filling in documents, you find yourself writing the same content in two places, keep it only in the SSOT location and replace the rest with a "details in [`NN.xxx.md`](NN.xxx.md)" link.

## Frontmatter Conventions

All documents declare `type` and `related_to` in YAML frontmatter.

### type

A single value indicating the document category, matching the **Category column of §Table of Contents 1:1** (single SSOT). Only the 7 values below are allowed.

| `type` value | Display name (category) | Meaning | Slots |
| :--- | :--- | :--- | :--- |
| `Meta` | Meta | Documentation index · convention hub · registries | 00 |
| `Overview` | Overview | Project-specific information fact sheet | 01 |
| `Foundation` | Foundation | Lowest-change-frequency reference docs referenced by all | 02–04 |
| `Layer` | Layer | Per-layer (UI · core / data) coding conventions | 05 |
| `Operations` | Operations | Build · verification · operations-time procedures · artifact locations | 06 |
| `Domain` | Domain | One feature domain (vertical slice) | `domains/` |
| `Process` | Process | One user scenario traced as a call chain | `processes/` |

> Slot numbers follow this template. Inserting a new core document shifts later numbers by +1 (rare); **the `type` value and the §Table of Contents Category column must always match**.

### related_to

Navigation hints to adjacent documents. Values are written as **file names within the same `docs/`** (e.g., `04.framework.md`), and only documents whose topics are actually adjacent are listed (2–6 per non-hub document recommended; avoid excessive linking).

- **Bidirectional symmetry**: links among the core documents 01–06 are kept symmetric. If A lists B, then B also lists A.
- **Exception — 00 (Meta)**: the hub that indexes all core documents (01–06) as inbound links. Other documents do not back-reference 00.
- **Exception — `domains/` · `processes/` (leaf)**: files there reference core documents **one-way** as `../NN.xxx.md`. Core documents do not back-reference individual leaf files; they aggregate only through this index's §Domains / §Processes tables.

## Content Rules

**Every document in this set is a permanent guide** — conventions and facts that do not change over time (technical policies, file structure, code conventions). The following must not be written anywhere in the set:

- Phase / PR / Sprint progress · completion · carry-over · retrospective · hotfix pinning (e.g., `(Phase 2-4 complete)`)
- PR-tracking work checklists (items tracking specific PR completion in `- [x]` / `- [ ]` form)
- Test ID pinning (citing per-PR/Sprint identifiers such as `T1~T19` / `V1~V10`)
- Time-stamped notes (e.g., date/version pinning like "applies since v2.3", "introduced 2026-05-15")

Progress and roadmap are **not part of this set**. If the project keeps a roadmap, it is a separate document outside the set (a `roadmap.md` under the next free number, `07.`) that no set document references.

However, the following are allowed as they fit the essence of a guide.

- **Operator/user guide-style checklists** — e.g., troubleshooting procedures in `06.build-ops`, the Change Checklist in `01.overview`
- **Future change notes** — e.g., a one-line note like `(extend at v3 migration time)`
- **`_(TODO — <what's needed>)_` placeholders** — unverified cells stating what is needed to fill them

## When Adding a Feature

1. Change Checklist section of `01.overview.md` — check the work order
2. Refer to the relevant layer's conventions (`05`), the framework mechanisms (`04`), and the feature's domain document (`domains/<name>.md`) if one exists
3. For build · verification, see the Verification Pipeline section of `06.build-ops.md`
4. If an external interface (API endpoint · command · Intent, etc.) changed, update `04` §5 Contract Catalog
5. If a new feature domain or a new representative scenario appeared, copy the matching `_template.md` to `domains/<name>.md` / `processes/<name>.md` and register it in §Domains / §Processes (no core number shift)

## When Editing Documents

- When a Foundation / Layer document changes, check that summaries in linked documents are current (edit only the SSOT original)
- Synchronize this index's tables (§Table of Contents · §Domains · §Processes) and category descriptions
- Keep `related_to` symmetric among 01–06 (§Frontmatter Conventions)

## File Naming Rules

- Core documents: two-digit numeric prefix + `.` (`00.`–`06.`), contiguous. Keep the category order (Overview → Foundation → Layer → Operations) aligned with prefix sorting. Only when inserting a new core document do subsequent prefixes shift by +1, which is rare.
- **`domains/` and `processes/` files do not use numbers** — `<name>.md` in kebab-case (`payments.md`, `hw-interface.md`, `checkout.md`). Under `docs/`, these two are the only subfolders by default. Each keeps its `_template.md` as the copy source.
- Document names are kebab-case English (`build-ops.md`, `layers.md`).
- **File names are fixed regardless of stack.** `04.framework.md` is never renamed per stack — stack differences are reflected only in the document's **title (H1) and content**. This keeps the table of contents and links unchanged across projects.
- Only this index (`00.INDEX.md`) is uppercase — emphasizing its meta role as the index.
