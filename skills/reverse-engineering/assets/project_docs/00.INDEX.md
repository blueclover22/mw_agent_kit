# Documentation Index — Shared Template (template)

> This document is the **index template for a documentation set that can be copied into other projects as-is**.
> In a new project, copy the entire set into `docs/`, then fill in this file's `<...>` placeholders for your project.
> For the procedure when writing/analyzing with Claude (AI), see [`CLAUDE.md`](CLAUDE.md) in the same folder.
>
> **Primary target stacks**: Spring Boot · web (React / Next.js) · Tauri (web frontend + Rust core) · Android.
> The same skeleton can be applied to other stacks (FastAPI / Electron, etc.).

---

This is the documentation index for the `<project-name>` project.
Files live under `docs/` with a fixed sort order via two-digit numeric prefixes (`01.`, `02.`, …), and this index provides the overall guide to categories and roles.

This set serves two purposes: **writing guides for new projects** and **analyzing existing projects**. Each document directly contains "this project's conventions/facts", and the same topic is never split across multiple documents (§Per-Topic SSOT).

When adding or removing documents, update this index's table, category guide, and `related_to` together.

## Reading Order

Document numbers are sorted by **change frequency** (Foundation → Status), which differs from the actual reading order. The following paths are recommended depending on your purpose.

- **Analyzing an existing project** — `12` (understand behavior via call chains) → `09` (structure · stack · environment variables) → `02` (architecture) → `05` (contracts) → `08` + `domains/` (feature domains) → `01` · `03` (terms · conventions). Record the "current facts (is)" observed in the code.
- **Writing guides for a new project** — `01`→`02`→`03` (establish conventions) → `04`·`05` → `06`·`07` (·`08`) → `09` → `10`·`11`.

> For the detailed procedure when writing/analyzing with AI (Claude), see [`CLAUDE.md`](CLAUDE.md) §2.

## Category Guide

### Meta (00)

Indexes all documents as inbound links; excluded from bidirectional symmetry (§Frontmatter Conventions).

### Foundation (01–05)

**Reference documents** with the lowest change frequency, referenced by all other documents. In case of conflict, Foundation takes precedence.

### Domain Guide (06–08)

Split along two axes.

- **Horizontal (layers) — 06 / 07**: UI layer / core·backend layer conventions. Fixed at one each per project.
- **Vertical (feature domains) — 08 + `domains/` folder**: documents **features/subsystems used only in this project**, such as `payments` · `hw_interface` · `local_db` (SQLite), as slices cutting across multiple layers. Since the count grows to N, keep one file per domain in the **unnumbered `domains/` folder** (`domains/<domain>-guide.md`), with `08.domains.md` serving only as its index. Adding a domain never shifts the core (09–13) numbers.

> Per-stack 06 / 07 mapping — see the table under §Table of Contents.

### Application (09)

The **fact sheet connecting Foundation + Domain Guide conventions to the current project**. Holds only project-specific information that has no home in other documents (Scope · Tech Stack · folder tree · environment variable keys · Change Checklist · Troubleshooting). **Conventions themselves are linked, not duplicated here.**

### Operations (10–11)

Covers procedures and artifact locations at build · deploy · run · operations · test time.

### Learning (12)

Traces the call chain from "user action → resulting output", not "where things are". **When analyzing an existing project, this is the best document to fill in first.**

### Status (13)

Highest change frequency; one-way dependency structure that no other document references. Time-stamped status pinning (dates · Phases · completion markers, etc.) is written only in this document (§Content Rules); when first authoring, do not reconstruct past completed work — write only the remaining backlog and future consideration items.

## Per-Topic SSOT (Single Source of Truth)

**The same topic is never split across multiple documents.** The original (SSOT) for each topic lives in exactly one place below; other documents keep only a one-line summary + link. This rule is the key to preventing duplication in the documentation set.

| Topic | SSOT (original) | Treatment in other documents |
| :--- | :--- | :--- |
| Naming conventions (files · variables · functions · types) | **03** §Naming | 01 covers only domain terms' *names*; 02 · 09 link only |
| Domain term definitions | **01** | Other documents link only |
| Architecture principles | **02** | 09 shows only this project's application diagram |
| External interface contracts (API · command · Intent) | **05** | 04 · 07 · 08 link only |
| Environment variable key list · value policy | **09** §Environment Variables | 10 covers only build-time injection; 04 only the loading mechanism |
| Build · verification pipeline | **10** | 09 · 11 link only |
| Test execution · conventions | **11** | 10 §Verification links only in its sequence |
| Progress status · completion · Phase | **13** | Forbidden in 00–12 |

Error handling is split by layer with mutual links (not duplication): **03** = general policy (types · propagation · logging), **04** = framework-level mechanisms, **07** = service · transaction boundaries.

> If, while filling in documents, you find yourself writing the same content in two places, keep it only in the SSOT location and replace the rest with a "details in [`NN.xxx.md`](NN.xxx.md)" link.

## Frontmatter Conventions

All documents (00–13) declare `type` and `related_to` in YAML frontmatter.

### type

A single value indicating the document category, matching the **Category column of §Table of Contents 1:1** (single SSOT). Only the 7 values below are allowed.

| `type` value  | Display name (category) | Meaning                                             | Slots (example) |
| :------------ | :------------ | :-------------------------------------------------- | :---------- |
| `Meta`        | Meta          | Documentation index · convention hub                | 00          |
| `Foundation`  | Foundation    | Lowest-change-frequency reference docs referenced by all | 01–05       |
| `DomainGuide` | Domain Guide  | Per-area (UI · backend · domain) reference conventions | 06–08       |
| `Application` | Application   | Project-specific information fact sheet             | 09          |
| `Operations`  | Operations    | Build · operations · test-time procedures · artifact locations | 10–11       |
| `Learning`    | Learning      | Code call-chain tracing learning material           | 12          |
| `Status`      | Status        | Progress tracking (time-stamping allowed, one-way)  | 13          |

> Slot numbers are examples based on this template. The category–number mapping may vary with project composition (adding/removing rows), but **the `type` value and the §Table of Contents Category column must always match**.

### related_to

Navigation hints to adjacent documents. Values are written as **file names within the same `docs/`** (e.g., `04.framework-guide.md`), and only documents whose topics are actually adjacent are listed (2–6 per non-hub document recommended; avoid excessive linking).

- **Bidirectional symmetry**: links among 01–12 are kept symmetric. If A lists B, then B also lists A.
- **Exception — 00 (Meta)**: the hub that indexes all documents (01–13) as inbound links. Other documents do not back-reference 00.
- **Exception — 13 (Status)**: a one-way structure that no other document references. Only `13→others` is allowed; `others→13` is forbidden.
- **Exception — `domains/` (leaf)**: `domains/<domain>-guide.md` references core documents **one-way** as `../NN.xxx.md`. Core documents do not back-reference individual domain files; they aggregate only through the `08.domains.md` index.

## Content Rules

**Progress status and development checklists are managed solely in [`13.roadmap.md`](13.roadmap.md).** All other documents (00–12) are maintained as permanent guides, and the following must not be written in them.

> Permanent guide: conventions that do not change over time (technical policies, file structure, code conventions). Progress that changes over time is managed only in 13.roadmap.md, preserving the scaffold nature of 00–12.

Rules for first authoring `13.roadmap.md`:

- Do not trace and reconstruct past completed work · Phases · Sprints · PRs · test IDs from existing code.
- When first authoring, write only the backlog remaining from now on, deferred decisions, adoption considerations, and questions to verify next.
- Facts already completed are reflected in 00–12's descriptions of the current structure and conventions, not written as history in 13.

- Phase / PR / Sprint progress · completion · carry-over · retrospective · hotfix pinning (e.g., `(Phase 2-4 complete)`)
- PR-tracking work checklists (items tracking specific PR completion in `- [x]` / `- [ ]` form)
- Test ID pinning (citing per-PR/Sprint identifiers such as `T1~T19` / `V1~V10`)
- Time-stamped notes (e.g., date/version pinning like "applies since v2.3", "introduced 2026-05-15")

However, the following are allowed as they fit the essence of a guide.

- **Operator/user guide-style checklists** — e.g., troubleshooting procedures in `10.build-ops-guide`, the Change Checklist in `09.project-guide`
- **Future change notes** — e.g., a one-line note like `(extend at v3 migration time)`
- **`_(TODO — <when>)_` placeholders** — empty sections stating when an unwritten section will be authored

## When Adding a Feature

1. Change Checklist section of `09.project-guide.md` — check the work order
2. Refer to the relevant area's Domain Guide (06 / 07 / 08) or Framework conventions (04 / 05)
3. For build · verification, see the Verification Pipeline section of `10.build-ops-guide.md`
4. If an external interface (API endpoint · command · Intent, etc.) changed, update `05.framework-api.md`

## When Editing Documents

- When a Foundation / Domain document changes, check that summaries in linked documents are current (edit only the SSOT original)
- Synchronize this index's (`00.INDEX.md`) table and category descriptions
- When adding a new feature domain — copy `domains/_template.md` to `domains/<domain>-guide.md` and register it in the §1 list of `08.domains.md` (no core number shift)

## File Naming Rules

- Prefix is a two-digit number + `.` (e.g., `01.`).
- Keep the category order (Foundation → Domain Guide → Application → Operations → Learning → Status) aligned with prefix sorting. Only when inserting a new core layer document (06/07-class) do subsequent prefixes shift by +1, which is rare.
- **Feature domains do not use numbers** — keep them as `<domain>-guide.md` in the `domains/` folder to avoid core number changes. Under `docs/`, `domains/` is the only subfolder by default.
- Document names are kebab-case English (`framework-guide.md`, `backend-guide.md`).
- **File names are fixed regardless of stack.** `04.framework-guide.md` · `05.framework-api.md` are also never renamed per stack — stack differences are reflected only in the document's **title (H1) and content**. This keeps the table of contents and links unchanged across projects.
- Only this index (`00.INDEX.md`) is uppercase — emphasizing its meta role as the index. (`01.Glossary.md` keeps uppercase by convention)

> **Promotion (compact → standard)**: as scale grows, split the folded sections back out — `05` (contracts) out of `04`, `07` (core) out of `06` — and add `11` (tests) (§Slim Profiles). If **analysis comes first**, add `12` (process-guide) first (the analysis entry point).

## Template Usage Guide (recommend deleting this section after applying to a new project)

1. Copy the entire set into the new project's `docs/`.
2. Change `<project-name>` in the opening text to the actual project name.
3. In the table of contents, delete only the unused rows (file names are fixed, so **leaving rows in place is still valid** — no renaming needed).
4. Fill in `<framework>` in the **title (H1) and content** of 04 · 05 with the actual stack name. **Do not change the file names `04.framework-guide.md` · `05.framework-api.md`** (see §Table of Contents "Stack-specific 04 / 05 / 06 / 07 / 10").
5. Map 06 · 07 to the project's layers, add feature domains as `<domain>-guide.md` in `domains/`, and register them in `08.domains.md`.
6. **Check each document's frontmatter** — update `type` (one of the 7 values) + `related_to` (adjacent documents, bidirectional symmetry).
7. **Template cleanup (last)** — delete all template-only scaffolding so only project documents remain:
   - The `> Template: …` notice block at the top of each document (common to all documents). However, `CLAUDE.md` · `domains/_template.md` are scaffolds that stay, so do not delete them.
   - This file's opening introduction block (`> This document is … template`) and this entire section (`## Template Usage Guide`).
   - Unused stack/domain example rows, unsubstituted `<...>`.
   - **Verify: `grep -rn '> Template:' docs/ --exclude=CLAUDE.md --exclude=_template.md` returns 0 hits.** (For the detailed procedure, see [`CLAUDE.md`](CLAUDE.md) §2 · §4.)

### Slim Profiles (recommended starting point)

The full set of 14 assumes multiple domains and multi-person collaboration. For solo/small web/Tauri/Android projects, **start with compact and expand to standard when needed.**

| Profile  | Included documents                                             | Suited for                        |
| :------- | :------------------------------------------------------------ | :-------------------------------- |
| compact  | `00` · `02` · `03` · `04` · `06` · `09` · `10` · `13` (8 docs) | Small single-stack apps (weak FE/BE split) |
| standard | All of `00`–`13` + `domains/`                                  | Production services · multi-domain · collaboration |

> **Rationale for the compact composition**: keep only the axes a small app truly needs — index (`00`) · structure (`02`) · conventions (`03`) · stack mechanisms (`04`) · UI (`06`) · fact sheet (`09`) · build/operations (`10`) · progress (`13`). Fold `05` (contracts) into `04`, `07` (core) into `06`, and omit `08` · `11` · `12`. Promotion path to standard: see §File Naming Rules.
