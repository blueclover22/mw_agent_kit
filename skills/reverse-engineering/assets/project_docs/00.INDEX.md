# Documentation Index — Shared Template (template)

> This document is the **index template for a documentation set that can be copied into other projects as-is**.
> In a new project, copy the entire set into `docs/`, then fill in this file's `<...>` placeholders for your project.
> For the procedure when writing/analyzing with Claude (AI), see [`CLAUDE.md`](CLAUDE.md) in the same folder.
>
> **Primary target stacks**: Spring Boot · web (React / Next.js) · Tauri (web frontend + Rust core) · Android.
> The same skeleton can be applied to other stacks (FastAPI / Electron, etc.).

---

This is the documentation index for the `<project-name>` project.
Files live under `docs/` with a fixed sort order via two-digit numeric prefixes (`01.`, `02.`, …), and this index provides the overall guide to categories and roles.

This set serves two purposes: **writing guides for new projects** and **analyzing existing projects**. Each document directly contains "this project's conventions/facts", and the same topic is never split across multiple documents (§Per-Topic SSOT).

When adding or removing documents, update this index's table, category guide, and `related_to` together.

### related_to

Navigation hints to adjacent documents. Values are written as **file names within the same `docs/`** (e.g., `04.framework-guide.md`), and only documents whose topics are actually adjacent are listed (2–6 per non-hub document recommended; avoid excessive linking).

- **Bidirectional symmetry**: links among 01–12 are kept symmetric. If A lists B, then B also lists A.
- **Exception — 00 (Meta)**: the hub that indexes all documents (01–13) as inbound links. Other documents do not back-reference 00.
- **Exception — 13 (Status)**: a one-way structure that no other document references. Only `13→others` is allowed; `others→13` is forbidden.
- **Exception — `domains/` (leaf)**: `domains/<domain>-guide.md` references core documents **one-way** as `../NN.xxx.md`. Core documents do not back-reference individual domain files; they aggregate only through the `08.domains.md` index. _(standard-only)_

## Content Rules

**Progress status and development checklists are managed solely in [`13.roadmap.md`](13.roadmap.md).** All other documents (00–12) are maintained as permanent guides, and the following must not be written in them.

> Permanent guide: conventions that do not change over time (technical policies, file structure, code conventions). Progress that changes over time is managed only in 13.roadmap.md, preserving the scaffold nature of 00–12.

Rules for first authoring `13.roadmap.md`:

- Do not trace and reconstruct past completed work · Phases · Sprints · PRs · test IDs from existing code.
- When first authoring, write only the backlog remaining from now on, deferred decisions, adoption considerations, and questions to verify next.
- Facts already completed are reflected in 00–12's descriptions of the current structure and conventions, not written as history in 13.

- Phase / PR / Sprint progress · completion · carry-over · retrospective · hotfix pinning (e.g., `(Phase 2-4 complete)`)
- PR-tracking work checklists (items tracking specific PR completion in `- [x]` / `- [ ]` form)
- Test ID pinning (citing per-PR/Sprint identifiers such as `T1~T19` / `V1~V10`)
- Time-stamped notes (e.g., date/version pinning like "applies since v2.3", "introduced 2026-05-15")

However, the following are allowed as they fit the essence of a guide.

- **Operator/user guide-style checklists** — e.g., troubleshooting procedures in `10.build-ops-guide`, the Change Checklist in `09.project-guide`
- **Future change notes** — e.g., a one-line note like `(extend at v3 migration time)`
- **`_(TODO — <when>)_` placeholders** — empty sections stating when an unwritten section will be authored

## File Naming Rules

- Prefix is a two-digit number + `.` (e.g., `01.`).
- Keep the category order (Foundation → Domain Guide → Application → Operations → Learning → Status) aligned with prefix sorting. _(profile — compact: in this line, replace `(Foundation → Domain Guide → Application → Operations → Learning → Status)` with `(Foundation → Domain Guide → Application → Operations → Status)`.)_ Only when inserting a new core layer document (06/07-class) do subsequent prefixes shift by +1, which is rare.
- **Feature domains do not use numbers** — keep them as `<domain>-guide.md` in the `domains/` folder to avoid core number changes. Under `docs/`, `domains/` is the only subfolder by default. _(standard-only)_
- Document names are kebab-case English (`framework-guide.md`, `backend-guide.md`).
- **File names are fixed regardless of stack.** `04.framework-guide.md` is never renamed per stack — stack differences are reflected only in the document's **title (H1) and content**. This keeps the table of contents and links unchanged across projects.
- `05.framework-api.md` follows the same fixed-name rule. _(standard-only)_
- Only this index (`00.INDEX.md`) is uppercase — emphasizing its meta role as the index.
- `01.Glossary.md` also keeps uppercase, by convention. _(standard-only)_

## Template Usage Guide (recommend deleting this section after applying to a new project)

1. Copy the entire set into the new project's `docs/`.
2. Change `<project-name>` in the opening text to the actual project name.
3. In the table of contents, delete rows for documents outside your chosen profile (see §Profiles), plus any other unused rows (file names are fixed, so **leaving rows in place is still valid** — no renaming needed).
4. Fill in `<framework>` in the **title (H1) and content** of `04` with the actual stack name; **do not change the file name `04.framework-guide.md`** (see §Table of Contents "Stack-specific 04 / 06 / 07 / 10"). In standard, do the same for `05`, keeping its file name unchanged too; in compact this step is skipped since the same content lives in `04` §5 Contract Catalog (see §Profiles folding table).
5. Map `06` to the project's UI layer. In standard, also map `07` to the project's core/backend layer, add feature domains as `<domain>-guide.md` in `domains/`, and register them in `08`; in compact, the core/backend layer goes into `06` §7 Core / Data Layer instead (see §Profiles folding table).
6. **Check each document's frontmatter** — update `type` (one of the 7 values) + `related_to` (adjacent documents, bidirectional symmetry).
7. **Template cleanup (last)** — delete all template-only scaffolding so only project documents remain:
   - The `> Template: …` notice block at the top of each document (common to all documents). However, `CLAUDE.md` · `domains/_template.md` are scaffolds that stay, so do not delete them.
   - This file's opening introduction block (`> This document is … template`) and this entire section (`## Template Usage Guide`).
   - Unused stack/domain example rows, unsubstituted `<...>`.
   - In §Per-Topic SSOT's `Treatment in other documents` column, where a cell reads `standard: … ; compact: …`, keep only your adopted profile's clause and drop its prefix.
   - **Profile cleanup** — keep only the material for your chosen profile: drop the §Table of Contents `Profile` column entirely (both profiles — it's template-time metadata, not part of the original table); in §Profiles, prune the profile table to your row (compact also keeps the folding table, since it is the promotion reference; standard drops the folding table); in §Per-Topic SSOT, delete the `SSOT (standard)` or `SSOT (compact)` column you did not adopt; delete every `_(profile — …)_` note — for a note marking a whole new section/subsection as not existing pre-fold, delete that entire section (heading included) when applying standard, and keep it (note only) when applying compact. For every `_(standard-only)_` note / `# standard-only` `related_to` comment: **applying compact** — delete the whole tagged row/line and the tagged `related_to` entry; **applying standard** — keep the row/line and the entry, just drop the `_(standard-only)_` / `# standard-only` markup itself (the content is exactly what standard needs).
   - **Verify: `grep -rn '> Template:' docs/ --exclude=CLAUDE.md --exclude=_template.md` returns 0 hits.** (For the detailed procedure, see [`CLAUDE.md`](CLAUDE.md) §2 · §4.)
   - **Verify (profile cleanup): `grep -rn '_(profile' docs/ --exclude=CLAUDE.md` and `grep -rn 'standard-only' docs/ --exclude=CLAUDE.md` both return 0 hits.** (`CLAUDE.md` §3 keeps a permanent `Profile` reference column, same reasoning as the `> Template:` exclusion above.)
